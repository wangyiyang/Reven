# 用友渐进替代与可扩展平台架构

> 版本：v1.0
> 日期：2026-07-19
> 状态：目标架构与迁移基线
> 上位文档：[AI 原生家电零售经营平台规格书](./erp-platform-spec.md)
> 远期规划：[CRM 等候选模块](./future-product-roadmap.md)

## 1. 结论

平台应具备最终替代现有用友的架构能力，但不能采用“大爆炸式”整体重写。推荐使用渐进替代模式：先建立数据防腐层和影子账，再按商品、销售、库存、采购、结算、财务的顺序逐模块接管。

核心纪律是：

> 同一租户、同一业务域、同一时间只能有一个记账主系统。

过渡期可以双读、影子计算和结果对账，但不能长期双写。每个模块必须通过独立退出门槛后，才能把主写权从用友切换到新平台。

## 2. “替代用友”的两层含义

用友不是单一产品，可能是 U8、U9、NC、T+ 或其他版本，不同产品和模块差异很大。当前 workspace 只能看到进销存导出结果，尚不能确认具体产品、版本、部署形态和接口能力。

### 2.1 经营系统替代

接管：

- 商品、客户、供应商和组织主数据。
- 销售、退货、换机、价格和业绩分摊。
- 库存、预占、在途、调拨、盘点和序列号。
- 采购、收货、退供和补货。
- 目标、提成、任务和经营分析。

财务总账仍在用友，新平台通过凭证或汇总接口向用友过账。这是优先目标。

### 2.2 完整 ERP 替代

在经营系统基础上继续接管：

- 应收、应付、收付款和费用。
- 存货核算、成本结转和财务子账。
- 会计凭证、科目、辅助核算和总账。
- 会计期间、结账、反结账和审计。
- 税务及监管相关输出。

架构按完整 ERP 的上限设计，但在获得完整业务样本、会计政策和专业验收前，不承诺财务模块上线。

## 3. 替代前必须完成的盘点

### 3.1 系统盘点

| 维度 | 必须确认 |
|---|---|
| 产品 | 用友产品线、版本、补丁和部署方式 |
| 模块 | 已启用的销售、库存、采购、财务等模块 |
| 定制 | 自定义字段、报表、插件、存储过程和外围系统 |
| 接口 | OpenAPI、Web Service、数据库只读、定时导出能力 |
| 规模 | 用户、组织、SKU、单据、流水和附件数量 |
| 运维 | 备份、容灾、关账窗口、升级和技术支持方式 |

### 3.2 业务盘点

- 单据类型、编号规则、状态和审批流程。
- 仓库、货位、批次、序列号和计量单位。
- 负库存、预占、在途、调拨和盘点规则。
- 销售退货、换机、赠品、返利和价格政策。
- 采购收货、退供、供应商返利和结算方式。
- 成本计价方法、成本调整和月末结转。
- 科目、辅助核算、凭证模板和会计期间。
- 权限、职责分离和关键审批人。

### 3.3 数据盘点

- 主数据编码、重复项、停用项和别名。
- 历史单据范围、附件、审计日志和期初余额。
- 未完成销售、采购、调拨、收付款和在途单据。
- 应收、应付、库存和总账的当前余额。
- 当前系统已知的数据质量问题。

未完成盘点前只能设计通用边界，不能编写最终迁移映射。

## 4. 架构策略

### 4.1 模块化单体优先

第一阶段采用模块化单体，而不是微服务：

- 一个部署单元降低事务、运维和调试成本。
- 每个领域拥有独立模块、数据表和应用服务。
- 跨模块只能调用公开应用接口或消费领域事件。
- 禁止跨模块直接写表。
- 数据库迁移按模块归档和审查。

当某个模块出现独立扩缩容、发布节奏、团队所有权或可靠性要求后，再沿现有边界拆分服务。

### 4.2 端口与适配器

领域逻辑不直接依赖用友、飞书、Excel 或某个数据库驱动：

```text
领域模块 -> 应用端口 -> 基础设施适配器

适配器示例：
YonyouAdapter / ExcelAdapter / FeishuAdapter / ObjectStorageAdapter
```

替换上游系统时只替换适配器和映射，不重写领域规则。

### 4.3 防腐层

用友字段、单据状态和编码先进入防腐层，再转换为平台标准命令或事件：

```mermaid
flowchart LR
    Yonyou["用友接口 / 导出 / 只读库"] --> Connector["连接器"]
    Connector --> Mapping["版本化映射"]
    Mapping --> Canonical["标准命令与事件"]
    Canonical --> Domain["领域模块"]
    Domain --> Outbox["Outbox"]
    Outbox --> Yonyou
```

领域代码不得出现用友表名、状态码或专有字段。

### 4.4 事件与一致性

- 模块内部使用数据库事务保证强一致。
- 跨模块通过版本化领域事件协作。
- 使用 Transactional Outbox 保证业务事实和待发布事件原子落库。
- 消费端使用 Inbox 和幂等键抵抗重复投递。
- 事件只陈述已经发生的事实，不携带执行任意代码的指令。
- 财务过账等关键链路提供对账任务，不依赖“最终大概一致”。

## 5. 目标模块边界

### 5.1 平台内核

平台内核提供所有领域共用但不包含具体业务规则的能力：

| 模块 | 职责 |
|---|---|
| 租户 | 隔离、套餐、功能开关和数据范围 |
| 身份权限 | 用户、角色、职责分离、代理和数据权限 |
| 组织 | 公司、门店、部门、组、员工及有效期 |
| 单据框架 | 编号、状态、附件、备注、关联和 revision |
| 工作流 | 审批、任务、超时、撤回和升级 |
| 规则 | 版本化 DSL、测试、发布和生效时间 |
| 期间 | 业务日期、会计期间、锁定和重开 |
| 审计 | 操作者、变更前后、来源和关联 ID |
| 集成 | API、Webhook、Outbox、Inbox 和连接器 |

平台内核不应演变为万能基类。只有两个以上领域共享且语义一致的能力才进入内核。

### 5.2 主数据

- 商品、SKU、型号、品牌、品类和计量单位。
- UPC、序列号、来源编码和别名。
- 客户、供应商、仓库、货位和价格表。
- 主数据合并、拆分、停用和生效日期。

主数据 ID 由平台生成，用友编码作为外部标识保存，不能继续把来源编码当全局主键。

### 5.3 经营领域

| 领域 | 聚合根/核心事实 | 主要事件 |
|---|---|---|
| 销售 | 销售订单、销货、退货、换机 | 销售确认、退货确认 |
| 定价 | 价格表、促销、授权价 | 价格发布、价格覆盖 |
| 库存 | 库存流水、预占、盘点、调拨 | 库存增加、扣减、锁定 |
| 采购 | 请购、采购单、收货、退供 | 采购确认、收货完成 |
| 履约 | 配送、安装、签收、售后 | 已发货、已安装、已关闭 |
| 激励 | 目标、业绩分摊、提成 | 业绩确认、提成锁定 |

### 5.4 财务领域

| 领域 | 职责 |
|---|---|
| 应收 | 客户应收、收款、核销和账龄 |
| 应付 | 供应商应付、付款、核销和账龄 |
| 资金 | 账户、收支、转账和日记账 |
| 存货核算 | 入库成本、出库成本、调整和结转 |
| 总账 | 科目、凭证、辅助核算、余额和期间 |
| 财务报表 | 试算平衡、损益、资产负债等输出 |

经营单据通过明确的过账策略生成财务子账和凭证，不允许 Agent 根据自然语言临时拼凭证。

## 6. 可扩展机制

### 6.1 稳定 API

- 外部 API 采用版本号和明确弃用周期。
- 命令与查询分离，写命令要求期望版本和幂等键。
- 分页、错误码、租户上下文和权限语义保持一致。
- API 契约测试随模块发布。

### 6.2 领域事件

- 事件名称使用已完成时态，例如 `inventory.stock_reserved.v1`。
- Schema 进入注册表并保持向后兼容。
- 消费者不能依赖未声明字段。
- 敏感字段不进入广播事件，使用引用和授权查询。

### 6.3 规则扩展

适合配置化的内容：

- 提成、目标、滞销、补货和审批条件。
- 商品分类、来源字段映射和凭证模板。
- 预警阈值、责任人路由和通知策略。

规则使用受限 DSL、版本、测试样本、审批和生效时间。禁止租户上传任意 Python/JavaScript 作为业务规则。

### 6.4 自定义字段

- 按实体类型定义字段，类型和校验明确。
- 支持可见性、必填性、索引和权限。
- 重要流程字段必须提升为正式模型，不能永久躲在 JSONB。
- 指标和 Agent 工具只能使用已登记、已授权的自定义字段。

### 6.5 工作流扩展

审批和任务可配置，但业务状态仍由领域模块控制。工作流可以批准“是否过账”，不能绕过领域约束直接把单据改成已过账。

### 6.6 连接器扩展

连接器实现统一契约：

- 身份验证和租户配置。
- 全量读取、增量游标和重试。
- 标准命令/事件映射。
- 限流、幂等、死信和对账。
- 健康状态和可观测性。

首批连接器由平台团队维护，不在 MVP 开放任意第三方插件执行代码。

## 7. 记账主权模型

平台维护 `system_of_record_registry`，按租户和业务域记录：

| 字段 | 含义 |
|---|---|
| `domain` | 销售、库存、采购、应收、应付、总账等 |
| `owner_system` | 当前主写系统 |
| `mode` | 观察、影子、主写、只读归档 |
| `effective_at` | 切换生效时间 |
| `cutover_id` | 对应迁移批次 |
| `rollback_until` | 允许受控回退的截止时间 |

所有写命令先检查当前域的主权。处于影子模式时平台只能计算和对账，不能产生正式外部效力。

## 8. 单个模块的接管状态机

```text
DISCOVERED
  -> MAPPED
  -> SHADOW_READ
  -> SHADOW_CALCULATE
  -> RECONCILED
  -> READ_SWITCHED
  -> WRITE_CUTOVER
  -> STABILIZING
  -> OWNED_BY_PLATFORM
  -> LEGACY_ARCHIVED
```

### 8.1 影子阶段

- 从用友读取相同事实。
- 新平台独立计算结果。
- 按日、单据、SKU、仓库和余额对账。
- 差异进入工作队列，不能用手工 Excel 覆盖后宣称通过。

### 8.2 切换阶段

- 冻结切换范围和业务时间窗口。
- 导入期初、未完成单据和必要历史。
- 完成最终增量同步和余额核对。
- 将该域主写权原子切换到平台。
- 用友侧该域改为只读或停止录入。

### 8.3 稳定阶段

- 每日执行数量、金额、余额和凭证对账。
- 监控错误率、性能、用户流程和外部集成。
- 在回退窗口内保留受控反向迁移能力。
- 稳定期通过后关闭用友对应写入口。

## 9. 建议接管顺序

### 阶段 A：防腐层和统一读取

- 完成用友盘点、接口验证和编码映射。
- 导入销售、库存和主数据，只读生成统一指标。
- 建立 Excel、API 和只读数据库三种适配路径。

### 阶段 B：商品与组织主数据

- 平台建立内部 ID、别名和有效期。
- 用友仍可作为来源，但所有新模块只引用平台 ID。
- 解决当前按商品名称和人员名单硬匹配的问题。

### 阶段 C：销售与经营协作

- 平台接管报价、销售、退货、分摊和任务。
- 用友暂时接收财务所需的销售结果或凭证。
- 销售域切换后停止两边开单。

### 阶段 D：库存与采购

- 接管预占、出入库、调拨、盘点、序列号和在途。
- 接管请购、采购、收货和退供。
- 库存数量、库存金额和未完成单据全部通过切换对账。

### 阶段 E：应收、应付和资金

- 接管收付款、核销、账龄和供应商结算。
- 平台运行财务子账，用友总账继续接收凭证。
- 子账余额与用友逐日对账。

### 阶段 F：存货核算和总账

- 确认成本方法、会计政策、凭证模板和期间流程。
- 影子运行至少一个完整月结周期。
- 完成试算平衡、子账总账和财务报表验收。
- 切换后将用友转为只读历史档案。

## 10. 财务替代的硬约束

### 10.1 复式记账

- 每张已过账凭证借贷必相等。
- 科目、币种、辅助核算和期间必须有效。
- 过账使用 Decimal 和明确舍入规则。
- 已过账凭证不可原地修改，只能冲销或更正。

### 10.2 子账与总账

```text
库存数量账 = 库存流水累计
库存金额账 = 存货核算累计
应收子账 = 客户往来余额
应付子账 = 供应商往来余额
所有子账控制科目 = 总账对应余额
```

任何不平都必须阻断关账，不能依赖人工备注解释。

### 10.3 期间控制

- 单据日期、业务日期和过账日期分开保存。
- 已关闭期间禁止普通用户补录和修改。
- 反结账属于高风险操作，需要职责分离和完整审计。
- 月结任务可重试但必须幂等。

### 10.4 库存成本

移动平均、月末平均、先进先出或其他方法必须由现有会计政策确认。成本算法需要黄金样本、并发入出库测试、负库存规则和月末重算能力。

## 11. 数据迁移策略

### 11.1 分层迁移

| 层 | 内容 | 用途 |
|---|---|---|
| 原始归档 | 用友导出、数据库快照、附件 | 审计和追溯 |
| 标准历史 | 标准化主数据和历史单据 | 查询和 Agent 分析 |
| 运营数据 | 未完成单据、当前余额和必要近期历史 | 新系统继续处理 |
| 期初数据 | 库存、应收、应付、资金和总账余额 | 切换记账起点 |

不是所有历史都需要装进高频交易表。完整历史可进入归档和只读模型，运营库保留继续业务所需数据。

### 11.2 对账维度

- 主数据数量、启停状态和编码映射。
- 单据数量、状态、数量、税额和含税/未税金额。
- SKU + 仓库 + 批次/序列号库存。
- 客户应收、供应商应付和账龄。
- 科目 + 辅助核算 + 币种余额。
- 未完成流程、在途和预占。

每次迁移生成签名报告，由业务负责人和财务负责人分别确认。

## 12. Agent 在替代过程中的边界

Agent 可以：

- 解释用友字段与平台字段的映射建议。
- 汇总迁移差异并定位到原始记录。
- 生成测试场景、对账说明和处理草稿。
- 查询某个模块当前主系统和切换状态。
- 辅助用户完成新旧流程迁移。

Agent 不可以：

- 自动接受余额或凭证差异。
- 自行切换记账主权。
- 自行修改期初余额、已过账凭证或已关闭期间。
- 根据自然语言绕过权限、审批或领域不变量。
- 把旧系统备注、附件或导入文件中的文本当作系统指令。

## 13. 部署演进

### 13.1 初期

- 模块化单体。
- PostgreSQL 单主库，按模块划分 Schema 或表所有权。
- 对象存储保存原始文件和附件。
- 独立 Worker 处理导入、同步和报表。
- Outbox/Inbox 保证集成可靠性。

### 13.2 需要拆分服务的信号

- 模块需要独立发布和回滚。
- 不同模块负载特征明显不同。
- 单模块故障需要隔离。
- 团队已经形成稳定模块所有权。
- 数据合规要求独立存储或部署。

拆分前必须先消除跨模块直接表访问，否则微服务只会放大现有耦合。

## 14. 每个模块的退出门槛

| 维度 | 必须满足 |
|---|---|
| 功能 | 高频、异常、撤销和重开流程通过验收 |
| 数据 | 主数据、单据、余额和未完成流程完整迁移 |
| 对账 | 约定周期内数量和金额差异为零或有签批 |
| 性能 | 峰值导入、查询和过账满足业务窗口 |
| 权限 | 职责分离、数据范围和高风险审批生效 |
| 审计 | 原始来源、变更、过账和切换全程可追溯 |
| 运维 | 备份恢复、监控、告警和故障演练通过 |
| 回退 | 回退窗口、数据补偿和责任人明确 |

任何一个维度未通过，都不能关闭用友对应模块。

## 15. 平台级验收目标

1. 新业务模块不依赖用友专有表名或状态码。
2. 租户定制通过规则、字段、工作流和连接器完成，不产生代码分支。
3. 跨模块写入全部通过公开接口或领域事件。
4. 同一业务域不存在长期双写。
5. 任意业务事实可追溯到来源、规则、操作者和过账结果。
6. 财务切换前至少完成一个完整期间的影子月结。
7. 用友停用后仍能以只读方式检索历史和导出审计资料。

## 16. 下一步输入清单

为了把目标架构转成可执行迁移计划，需要补充：

1. 用友产品名称、版本、部署方式和许可证模块。
2. 管理员可提供的接口文档、数据库只读权限或标准导出清单。
3. 销售、采购、库存、应收、应付、凭证各一组脱敏样本。
4. 当前科目表、成本计价方法、结账流程和财务负责人确认。
5. 外围系统清单：飞书、支付、银行、物流、电子发票、京东等。
6. 当前用友最不可替代和最痛苦的三个流程。
