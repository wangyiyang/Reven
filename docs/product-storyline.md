# 产品主故事线

> 版本：v1.0
> 日期：2026-07-19
> 状态：统一产品叙事与决策基线
> 下位文档：[五阶段产品需求文档](./prd.md)

## 1. 一句话故事

我们不是把一批 Excel 报表搬到网页上，而是把已经在 OpenClaw 中验证过的经营知识，沉淀成一个拥有可信事实、统一规则和智能协作能力的平台；平台先解决每日经营问题，再逐模块取得记账主权，最终具备替代用友并生长出 CRM 等行业应用的能力。

## 2. 故事从哪里开始

当前用户已经有用友，也已经有 OpenClaw，但两者之间仍存在一段依赖人的工作：

```text
用友导出 Excel
  -> 人在飞书发送文件
  -> Agent 判断该用哪个文件和脚本
  -> Python 临时计算
  -> 飞书返回日报、库存、滞销、目标或提成结果
```

这套方式不是失败的原型。独立复算已经证明，部分销售日报、库存预警和提成公式能够与原始数据完全对齐。三个月持续纠错形成的净额、组合销售、空调套数、可用量、在途、残机库和滞销清单等口径，是当前最有价值的业务资产。

问题在于，这些知识还没有成为系统能力：它们散落在脚本、Skill、配置、记忆和人的经验中。

## 3. 真正的转折点

### 3.1 不是 Excel 太多，而是事实没有稳定下来

workspace 中有 109 个 Excel，但独立聚类发现，核心销货表主要是 5 种结构、库存表主要是 3 种结构。格式仍会变化，却不需要建设无限通用的解析引擎；十个以内的版本化模板可以覆盖当前主要输入。

更根本的问题是：同一用友单据在日报发出后可能被改部门、改金额或补录退货。历史报告与后来导出的“当前值”因此不一致，且无法回答什么时候、由谁、为什么改变。

所以平台首先要解决的不是“怎么读 Excel”，而是：

- 原始文件能否保持不可变。
- 同一单据的来源版本能否完整保存。
- 修正、冲销和重算能否被审计。
- 每个指标能否追溯到当时的事实和规则。

### 3.2 不是 Agent 不够聪明，而是规则没有唯一来源

现有目录中存在多版人员分组、多版滞销清单、多套完成率、空调和分摊逻辑。最新 v2 脚本仍然过滤负金额，并把商品说明解析成业务员。

这说明继续优化 Prompt 或增加 Agent 数量不能解决问题。金额、库存、提成和状态转换必须由确定性服务执行；规则必须成为带版本、生效时间、测试和发布状态的数据。

### 3.3 不是所有现有数据都能成为主数据

- 京东 B2B 与门店商品体系的严格匹配率约为 5.3%，不能作为商品或价格主数据。
- UPC 存在缺失和非唯一，只能作为候选标识。
- 滞销当前是人工维护清单，不是动态算法，应先忠实版本化。
- 提成公式可以部分还原，但约 32% 行缺少权威底表依据，因此只能先做试算和未匹配治理。

平台必须区分“已有数据”“可信事实”和“权威主数据”，不能简单把所有文件导进数据库后宣布完成。

### 3.4 安全不是上线前补做的事项

workspace 已发现多类明文凭据、客户联系电话和送货地址，以及附件内容中的 Prompt Injection 样本。安全和隐私必须成为第一阶段的进入门槛，而不是产品完成后的加固项目。

## 4. 我们决定建设什么

产品定位统一为：

> 面向多门店家电经销商的 AI 原生经营平台：吸收持续变化的 Excel，沉淀可信业务事实和版本化规则，通过工作台与 Agent 完成查询、诊断、纠错、审批和协作，并按业务域逐步替代用友。

它与三个相邻概念的区别：

| 形态 | 能做什么 | 为什么不是终点 |
|---|---|---|
| 报表平台 | 展示已有数据 | 不拥有事实和规则，无法处理纠错与操作闭环 |
| 完整 ERP 重写 | 一次覆盖销售、库存、采购和财务 | 当前缺少采购、财务和用友接口证据，风险不可控 |
| AI 聊天助手 | 理解问题并生成回答 | 不能承担金额、库存和记账主权 |
| AI 原生经营平台 | 拥有可信事实、规则、指标、操作与智能入口 | 是当前可验证、可演进的正确路径 |

## 5. 产品如何一步步成立

```mermaid
flowchart LR
    A["安全与黄金样本"] --> B["可信数据层"]
    B --> C["经营工作台"]
    C --> D["智能协作闭环"]
    D --> E["逐模块接管用友"]
    E --> F["CRM / 售后 / WMS / SRM"]
```

### 第一层：安全与事实基线

先轮换凭据、保护个人信息、确认业务口径，并把历史纠错转成黄金案例。没有业务确认的期望结果，就没有资格重写现有逻辑。

### 第二层：可信数据层

不强迫用户统一 Excel。文件进入不可变原始层，已知格式匹配版本化模板，未知格式由 Agent 建议映射、用户确认；正式提交前完成行数和金额守恒。事后改单产生新版本，不覆盖历史。

### 第三层：经营工作台

平台开始拥有销售、退货、换机、分摊、商品、库存、目标和提成试算事实。用户首先看到的是待处理异常，而不是装饰性 Dashboard。页面、飞书和 Agent 使用同一个指标语义层。

### 第四层：智能协作闭环

Agent 查询指标、解释异常、定位证据和生成操作草稿；确定性服务负责计算和状态；有权限的人负责模板发布、规则确认和高风险审批。至少一条业务线完成“发现问题到处理完成”的闭环。

### 第五层：逐模块接管用友

每个领域独立经历影子读取、影子计算、对账、切读、切写和稳定期。同一业务域在任一时刻只有一个主写系统。先争取经营系统替代，再根据财务样本和会计政策决定是否接管完整总账。

## 6. 当前 MVP 的边界

### 必须进入

- 销货与库存 Excel 的弹性导入。
- 原始文件、原始行、修正、单据版本和指标血缘。
- 商品主数据及来源别名治理。
- 销售、退货、换机和二人组/三人组分摊。
- 库存快照、可用量、在途、负卖、残机和滞销清单。
- 月度目标和累计完成率。
- 提成试算、底表管理入口和未匹配治理。
- 经营异常工作台、飞书通知和只读 Agent。
- 权限、审计、幂等、隐私和黄金回归。

### 明确不进入

- 正式提成结算和工资发放。
- 采购订单、供应商结算和财务总账。
- Agent 直接调价、调库存、结算或执行任意 SQL。
- CRM、售后、WMS、SRM、OMS、会员和营销。
- 任意代码插件、万能单据引擎和无证据的微服务拆分。

## 7. 架构主线

架构选择服务于产品故事，而不是反过来：

- 使用模块化单体和后台 Worker 起步。
- PostgreSQL 保存强类型业务事实，JSONB 只保存原始行和有限扩展。
- 对象存储保存不可变原始文件。
- 跨模块通过公开 API 或版本化领域事件协作。
- 指标语义层是页面、Bot 和 Agent 的唯一经营数字入口。
- 规则采用版本化数据、受限 DSL 和确定性求值器。
- RAG 只检索非结构化资料，不代替交易查询。
- MVP 不依赖 LangChain；LangGraph 只有在出现真实跨会话复杂编排后再引入。
- 数据模型保留 `tenant_id`，首发按单租户实现，复杂 RLS 延后到 SaaS 需求成立时。

## 8. 最终可以长成什么

当核心事实和主数据稳定后，平台可以自然生长：

- CRM 使用统一 `customer_id` 管理客户、线索、商机和复购。
- 售后使用订单、客户、SKU 和序列号管理配送、安装、维修和保修。
- WMS 使用仓库、货位、序列号和库存事件管理物理作业。
- SRM 使用供应商、商品、库存和成本形成采购闭环。
- OMS 连接多个订单来源和履约流程。

这些是远期候选模块，不是当前范围。启动新模块必须同时满足真实流程、真实样本、清晰事实所有权和可量化退出条件。

## 9. 北极星和成功标准

北极星不是“每天有多少人和 Agent 对话”，而是：

> 可信经营闭环覆盖率：从事实产生、规则计算、异常发现到任务完成，能够被平台完整承载和追溯的核心业务比例。

阶段性成功标准：

| 维度 | 目标 |
|---|---|
| 数据 | 重复导入为零，金额和分摊守恒 |
| 事实 | 事后变化 100% 形成来源版本和差异 |
| 规则 | 修改一处、版本生效、黄金案例自动回归 |
| 使用 | 用户连续两周无需临时脚本生成核心日报 |
| Agent | 数字回答全部携带范围、指标版本和来源证据 |
| 操作 | 高风险动作全部经过权限、确认和审计 |
| 替代 | 每个接管领域只有一个主写系统 |

## 10. 尚未解决的关键问题

1. 用友具体产品、版本、模块、部署方式和接口能力。
2. 提成底表的权威文件、维护人和变更流程。
3. 人员分组、滞销清单和月度目标的权威维护角色。
4. 采购、供应商、应收应付、凭证、成本和关账样本。
5. 首发单商家验证后，何时具备转向 SaaS 多租户运营的条件。
6. 长期替代终点是经营系统，还是包含完整财务 ERP。

这些问题不会阻塞安全基线和可信数据层，但会阻塞相应领域进入产品范围。

## 11. 我们共同遵守的判断

1. 先让事实可信，再增加智能。
2. 先验证真实流程，再建设通用能力。
3. 先单体保持边界，再根据真实压力拆分。
4. 先影子对账，再切换记账主权。
5. Agent 提高理解和协作效率，不取代业务不变量和人的责任。
6. CRM 等未来能力要被记住，但不能污染当前 MVP。
