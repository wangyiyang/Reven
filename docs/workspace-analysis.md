# OpenClaw Workspace 深度诊断

> 版本：v2.0
> 分析日期：2026-07-19
> 分析对象：`workspace/` 中的业务文件、脚本、Skill、记忆与既有输出

## 1. 结论

该 workspace 不是一个普通聊天助手目录，而是围绕家电零售经营形成的“影子业务系统”：用户通过飞书发送进销存导出的 Excel，OpenClaw 临时选择或编写 Python 脚本，完成销售、库存、滞销、空调、目标和提成分析。

现阶段最重要的问题不是缺少更多 Agent，而是缺少四个系统基础：

1. 统一且可追溯的业务数据模型。
2. 可复用、可版本化、可回归验证的业务规则。
3. 能容忍不固定 Excel 的数据接入与纠错工作台。
4. 权限、审计、隐私和凭据治理。

因此，不应直接把现有脚本搬进数据库，也不应一次性重做大而全 ERP。推荐先建设“AI 原生家电零售经营平台”，由平台逐步接管销售、库存、采购、结算和财务，最终具备替代现有用友的能力。

## 2. 分析范围与限制

本次分析采用以下证据：

- `workspace/` 全量文件结构与文件元数据。
- 代表性销售、库存、序列号、价格和提成 Excel 的 Sheet、表头与字段。
- 三连报告、库存预警、完成率和提成脚本。
- Skill 中记录的业务口径。
- 历史记忆中反复出现的纠错场景。
- 使用 2026-07-18 销货文件对 `daily-triple-report-v2` 进行只读运行验证。

限制：现有 workspace 没有完整采购、供应商、应收应付、总账、配送安装和售后数据，也无法可靠判断具体用友产品版本，因此不能据此直接设计这些模块的最终流程和接口。

## 3. 用户与经营场景

### 3.1 已确认画像

| 维度 | 内容 |
|---|---|
| 经营主体 | 两个门店（门店 A、门店 B，已匿名） |
| 团队 | 15-18 人销售团队，按 A/B/C/D 分组 |
| 主营 | 空调、冰箱、洗衣机、电视、厨卫和小家电 |
| 品牌 | 格力、美的、海尔、晶弘、美菱、西门子、TCL、长虹、创维、康佳、华为等 |
| 仓库 | 1/2 号正品库、3 号残机库、4 号辅助库 |
| 工作入口 | 飞书群聊、Excel 文件、OpenClaw Agent |
| 上游系统 | 现有进销存系统，以 Excel 导出为主要接口 |

### 3.2 高频工作流

| 工作流 | 输入 | 关键结果 |
|---|---|---|
| 每日三连 | 销货单明细表 | 销售日报、空调分析、滞销机分析 |
| 月度目标 | 月累计销货单、目标 | 分组/个人完成率、日均缺口 |
| 库存预警 | 现存量、当日销售 | 负卖、清零、零可用、在途覆盖 |
| 库龄动销 | 库存、出入库、序列号 | 新到货、滞销、死库存、残机 |
| 价格分析 | 价格单、京东 B2B 数据 | 型号、采购价、市场价、UPC |
| 提成核算 | 销货单、成本/提成底表 | 计件、利润提成、毛利、未匹配商品 |

这些工作流已经覆盖了“销售事实、库存事实、商品识别、组织归属、价格成本、激励规则”六个核心领域，具备建设经营平台的真实业务基础。

## 4. 数据资产实测

### 4.1 文件规模

| 类型 | 数量 | 说明 |
|---|---:|---|
| Excel | 109 | 总体积约 9.51 MB |
| 销货相关 Excel | 72 | 日报、累计、提成原始数据等 |
| 库存相关 Excel | 25 | 现存量、库存分析和输出表 |
| 序列号 Excel | 3 | 单台设备生命周期和库房流转 |
| Python | 41 | 报表、下载、分析和记忆处理 |
| Markdown | 84 | Skill、记忆、日记和规则 |
| TSV | 5 | 京东 B2B 商品、价格、订单和 UPC |
| JSON | 10 | 配置、聚合结果和中间产物 |

按真实字段结构重新聚类后，核心销货单为 5 种结构、现存量查询为 3 种结构。此前统计的 62/13 种“签名”混入了日期、参数和标题行，夸大了格式数量。Excel 仍会变化，但当前可用十个以内的版本化模板覆盖主要输入，无需建设无限通用解析引擎。

### 4.2 数据质量现状

- 发现 9 组内容完全相同但文件名不同的 Excel。
- 发现 1 个损坏的 Excel：`downloads/销货单明细表7.1-7.13.xlsx`。
- 同一日期可能同时存在日报、累计表、重命名文件和 v2 文件。
- 销货表包含多行标题、重复列名、零金额外机、负数退货和组合销售。
- 库存表存在多级表头，并同时提供现存、可用、采购在途、调拨在途、待入、待出等状态。
- 商品编码在不同报表之间不稳定，历史 Skill 已经退化为按商品名称关联。
- 销售文件包含客户姓名、联系电话和地址，属于需要严格控制的个人信息。

这意味着导入系统必须同时解决格式识别、来源去重、单据幂等、字段映射、主数据匹配和隐私保护，而不仅是 `pandas.read_excel()`。

## 5. 代码与业务口径实测

### 5.1 代码规模和工程质量

| 项目 | 结果 |
|---|---:|
| Python 文件 | 41 |
| 超过 50 行的函数 | 23 |
| 绑定 `/root/.openclaw/workspace` 的文件 | 17 |
| 疑似硬编码凭据/文件标识 | 8 处 |
| 自动化测试 | 0 |
| 项目依赖/构建配置 | 未发现 |

脚本并非单纯复制。随着用户持续纠错，不同文件逐步形成了互不一致的业务口径，例如人员分组、退货、二人组、空调套数、滞销型号和在途覆盖。这种“逻辑漂移”比代码重复本身风险更高。

### 5.2 最新样本验证

使用 `销货单明细表_7.18.xlsx` 运行 `skills/daily-triple-report-v2/process.py`：

| 指标 | 结果 |
|---|---:|
| 有效零售明细 | 77 行 |
| 单据 | 34 张 |
| 销售净额 | 159,308.68 元 |
| 仅正金额合计 | 164,875.18 元 |
| 被忽略的负金额 | -5,566.50 元 |
| 二人组记录 | 11 行 |
| 三人组记录 | 4 行 |

程序最终输出 164,875.18 元，原因是销售日报先执行了 `含税金额 > 0` 过滤，与“退货按净额抵扣”的业务规则直接冲突。

组合销售解析还产生了以下错误类型：

- 把“业务员 + 商品说明”整体识别为业务员。
- 带负号或小数格式异常时解析失败。
- `三人组` 没有进入正式拆分逻辑。
- 白名单只校验原始业务员字段，未校验拆分后姓名。

因此，现有 v2 可以作为历史规则来源，不能作为无需验证即可迁移的成熟内核。

## 6. 根因分析

### 6.1 业务事实和报表结果混在一起

现有脚本直接从 Excel 计算最终文本，没有稳定保存：

- 原始文件和原始行。
- 标准销售单及明细。
- 退货与原销售的关系。
- 组合销售的分摊记录。
- 规则版本及生效时间。
- 每个指标引用的业务事实。

结果出现差异时，只能重新翻文件和脚本，无法沿数据血缘定位原因。

### 6.2 业务规则靠自然语言和复制代码传播

人员分组、滞销清单、目标、排除项和组合销售规则同时存在于 Skill、JSON、脚本和记忆中。多个来源没有优先级和生效日期，导致“最新正确口径”无法被系统回答。

### 6.3 缺少稳定的商品与组织主数据

商品同时以存货编码、名称、型号、UPC 和序列号出现，名称又承担了品牌、品类和型号解析。业务员分组也会随月份和规则变化。没有主数据及别名表，就只能不断增加正则和关键词。

### 6.4 LLM 被用于不适合的环节

LLM 擅长理解问题、解释结果和生成建议，不适合承担金额汇总、库存结余和提成结算。历史错误大多不是模型不会算，而是：

- 未确认业务语义便做出假设。
- 数据格式改变后沿用旧规则。
- 对不可信文本执行了过度自由的解析。
- 没有黄金数据和自动回归。

### 6.5 缺少安全边界

当前目录存在以下 P0 风险：

- 飞书应用、LLM 服务和京东相关凭据以明文出现在脚本或配置中，应立即轮换并迁移到环境变量或密钥管理服务。
- 没有仓库级 `.gitignore`，本地环境文件和业务数据可能被误提交。
- 原始 Excel 包含客户姓名、电话、地址及员工薪酬等个人信息，缺少字段脱敏、下载权限和留存策略。
- 记忆和文档中可能包含形似系统指令的文本。未来 Agent 必须将附件内容视为不可信数据，不能把数据内容当运行时指令执行。

## 7. 现有设计文档的主要缺口

旧版 ERP 规格有正确方向：确定性管道、数据库、Web 和飞书双入口。但仍有五个结构性问题：

1. 产品范围实际是报表 Dashboard，却命名为 ERP。
2. 数据模型只保存拆分后的销售行，丢失原始单据和分摊血缘。
3. `is_stagnant` 等时变规则被固化在销售事实上，无法按历史规则重算。
4. 验证方案主要与旧脚本输出对比，而旧脚本本身已经被证明可能错误。
5. 将 LLM 缩减为通知润色，没有利用 Agent 在查询、诊断、规划和受控执行上的价值。

## 8. 可建设能力与证据边界

### 8.1 证据充分，可优先建设

- 销售单、退货、换机和销售业绩分摊。
- 商品、型号、UPC、序列号和别名管理。
- 库存快照、可用量、在途、调拨和残机分析。
- 滞销策略、库存预警和补货建议。
- 价格、成本、毛利和市场价格对比。
- 月度目标、提成规则和结算辅助。
- 飞书通知、自然语言查询和异常协作。

### 8.2 证据不足，需业务调研后设计

- 采购订单、收货、退供和供应商结算。
- 应收、应付、收款、付款和财务总账。
- 配送、安装、维修和售后工单。
- 会员、营销、促销和客户生命周期。

## 9. 产品定位建议

近期产品先作为“现有用友之上的 AI 原生经营与操作层”，长期按业务域渐进替代用友：

```text
过渡期用友：尚未迁移领域的记账主系统
新平台：从导入治理和经营协作开始，逐模块成为记账主系统
Agent：理解、查询、解释、规划、发起受控动作
```

替代采用逐模块接管：同一业务域在任一时刻只能有一个主写系统。平台从第一版保留租户隔离、稳定领域边界和事件接口，但仍先围绕当前用户验证，不提前建设任意插件或通用财务能力。

## 10. 优先级

| 优先级 | 工作 | 成功标准 |
|---|---|---|
| P0 | 凭据轮换、数据隔离、黄金样本 | 无明文密钥，关键历史案例可复现 |
| P0 | 弹性 Excel 导入与对账 | 重复导入为零，导入差异可解释 |
| P1 | 标准业务模型和规则版本 | 原始行到指标全链路可追溯 |
| P1 | 经营工作台 | 异常集中处理，不再依赖临时脚本 |
| P2 | 只读经营 Agent | 回答均引用指标、规则和单据证据 |
| P2 | 受控操作 Agent | 高风险写操作全部确认并审计 |
| P3 | 用友防腐层与模块接管 | 逐步减少 Excel，每次只切换一个业务主系统 |

## 11. 待确认的产品决策

后续设计需要业务方确认：

1. 产品首先服务单个商家，还是按 SaaS 多租户销售。
2. 当前用友的具体版本、部署方式、已启用模块和可用接口。
3. 销售、库存、提成三条业务线中，哪一条最先形成操作闭环。
4. 哪些角色使用 Web，哪些角色只通过飞书处理任务。
5. 最终替代范围是否包含财务总账、税务和监管报表。
