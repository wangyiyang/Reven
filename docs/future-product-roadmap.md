# 远期产品路线

> 版本：v1.0
> 日期：2026-07-19
> 状态：候选路线，不属于当前 MVP 承诺
> 上位文档：[AI 原生家电零售经营平台规格书](./erp-platform-spec.md)

## 1. 记录目的

本文记录平台未来可能生长出的业务系统，防止在完成 ERP 基础后遗忘已经识别的产品机会。

这些内容是方向性 backlog，不代表已经确定开发范围、顺序或上线时间。当前优先级仍是：

1. 弹性 Excel 导入和数据可信层。
2. 销售、商品、库存、目标和提成基础能力。
3. 经营工作台和受控 Agent。
4. 逐模块接管并最终替代用友。

只有当前阶段达到验收门槛后，才评估本文中的后续模块。

## 2. 平台生长方式

未来能力分为三层：

```text
平台内核：租户、身份、组织、权限、工作流、规则、审计、集成
业务模块：ERP、CRM、WMS、SRM、售后、营销等独立领域
行业应用：家电配送安装、保修、清洗、以旧换新、滞销处置等
```

扩展不以“增加插件数量”为目标，而以稳定业务边界为前提：

- 每个模块拥有自己的业务事实、规则和生命周期。
- 模块共享平台身份和主数据 ID，不共享内部表。
- 跨模块通过公开 API 和版本化领域事件协作。
- 租户差异优先通过规则、字段和工作流配置解决。
- 不为单个客户创建长期代码分支。

## 3. 候选模块地图

| 模块 | 解决的问题 | 主要依赖 | 启动信号 |
|---|---|---|---|
| CRM | 客户、线索、商机和跟进分散 | 客户主数据、销售事实、权限 | 销售数据稳定且开始记录跟进 |
| 售后服务 | 配送、安装、维修和保养脱节 | 客户、商品序列号、订单 | 服务状态已能结构化采集 |
| WMS | 仓库作业、货位、盘点效率不足 | 商品、仓库、库存流水 | 现有库存账稳定且需要仓内作业 |
| SRM/采购 | 供应商、询价、采购和返利分散 | 供应商、商品、库存、成本 | 补货建议需要形成采购闭环 |
| OMS/履约 | 多渠道订单、配送和安装难协调 | 销售、库存、客户、售后 | 出现多个稳定订单渠道 |
| 营销自动化 | 客群触达和效果无法归因 | CRM、客户授权、活动归因 | 客户数据合规且有明确运营团队 |
| 会员与权益 | 复购、积分和权益缺少统一管理 | CRM、订单、营销 | 会员策略经过业务验证 |
| 计划与预测 | 补货和目标仍依赖经验 | 高质量销售、库存、采购历史 | 数据覆盖完整季节周期 |
| 经营数据产品 | 多门店、多租户需要统一决策 | 指标语义层、权限、审计 | 核心指标稳定并可跨组织比较 |

## 4. CRM 候选设计

### 4.1 定位

CRM 不另建孤立客户库，而是平台中的客户关系领域：

```text
ERP：记录已经发生的交易
CRM：记录客户关系、需求和未来机会
售后：记录交付后的服务生命周期
```

三者共享平台 `customer_id`，但分别拥有自己的数据和状态机。

### 4.2 能力分层

#### 客户 360

- 客户、家庭、联系人和地址。
- 购买、退换货、服务和沟通历史。
- 重复客户识别、合并和拆分。
- 客户授权、触达偏好和退订状态。

#### 线索与商机

- 线索来源、意向品类、预算和预计购买时间。
- 负责人、跟进记录、下一步和超时提醒。
- 报价、商机阶段、输单原因和成交归因。
- 商机成交后创建 ERP 销售草稿。

#### 家电生命周期

- 配送、安装、保修、维修和清洗状态。
- 保修到期、滤芯更换和保养提醒。
- 以旧换新和生命周期换购机会。
- 商品序列号与客户设备绑定。

#### 复购与交叉销售

- 基于已购品类和生命周期生成候选机会。
- 识别长期未跟进、高价值和服务异常客户。
- 建议只作为任务草稿，不自动给客户贴敏感标签。

#### 营销自动化

- 客户分群、活动、优惠和渠道触达。
- 频率限制、授权检查、退订和效果归因。
- 在客户授权与数据治理完成前不启用自动触达。

### 4.3 关键事件

| 事件 | 消费方动作 |
|---|---|
| `sales.sale_completed.v1` | CRM 更新购买历史 |
| `sales.return_completed.v1` | CRM 更新退货和体验记录 |
| `crm.opportunity_won.v1` | ERP 创建销售草稿 |
| `service.installation_completed.v1` | CRM 更新设备生命周期 |
| `service.warranty_expiring.v1` | CRM 创建关怀任务 |
| `crm.customer_merged.v1` | 各模块更新客户引用 |

### 4.4 CRM MVP 候选

未来首次建设 CRM 时，优先考虑：

1. 客户主档和重复客户合并。
2. 购买、退换货和服务历史。
3. 跟进任务、负责人和到期提醒。
4. 配送、安装和保修状态。
5. 复购与售后提醒草稿。
6. 飞书“今日待跟进客户”。
7. Agent 查询和跟进摘要。

暂不优先建设复杂营销自动化、积分商城或全渠道客服。

## 5. 售后与履约候选设计

家电行业的售后和履约应作为独立领域，而不是销售订单上的几个状态字段：

- 配送预约、装车、签收和异常。
- 安装预约、工程师、完工和材料。
- 维修、保修判定、配件和回访。
- 客户设备、序列号和服务历史。
- 残机、退换机和厂家责任追踪。

销售完成后生成履约需求，履约完成后更新客户设备；库存只消费明确的出库和退回事件。

## 6. WMS 候选设计

WMS 只有在库存账稳定后才值得建设。候选能力包括：

- 仓库、库区、货位和容器。
- 收货、上架、拣货、复核、出库和移库。
- 序列号扫描、盘点和差异处理。
- 波次、任务分配和作业绩效。
- 正品、残机、待检和锁定库存状态。

ERP 库存模块拥有数量和价值账；WMS 拥有仓内物理作业。两者通过库存作业事件协作，不能各自维护一套不可对账的库存。

## 7. SRM 与采购候选设计

- 供应商档案、品牌授权和结算条件。
- 询价、比价、采购建议和采购订单。
- 收货、退供、供应商返利和对账。
- 交期、到货率、质量和价格表现。
- 京东 B2B 等外部价格和订单连接器。

Agent 可以生成补货和比价草稿，但采购确认、调价和付款始终需要业务权限与审批。

## 8. Agent 的跨模块角色

Agent 作为统一交互层，可以跨模块理解问题，但不能拥有跨模块写表权限：

| 场景 | Agent 行为 |
|---|---|
| “哪些客户买了空调但还没安装？” | 查询销售和售后，返回证据 |
| “生成本周待跟进客户” | 生成 CRM 任务草稿 |
| “哪些型号需要补货？” | 查询销售、库存和采购在途 |
| “给供应商生成采购建议” | 生成采购草稿并进入审批 |
| “自动给这些客户发消息” | 检查授权和频控，仍需确认 |

跨模块查询通过指标和查询 API，跨模块动作通过领域命令、审批和事件完成。

## 9. 共享能力的建设边界

只有满足以下条件，能力才进入平台内核：

1. 至少两个模块确实需要。
2. 在不同模块中的业务语义一致。
3. 可以形成稳定契约和权限边界。
4. 不包含某个领域专属状态转换。

例如用户、组织、审计可以共享；销售订单、售后工单和采购单不能抽象成一个“万能业务单”。

## 10. 启动后续模块的门槛

评估新模块前需要满足：

- 当前核心模块已经达到数据对账目标。
- 新模块存在明确责任人和高频真实流程。
- 可取得足够样本，不依赖纯想象设计。
- 与现有模块的事实所有权已经明确。
- 能定义可量化的业务结果和退出条件。
- 不会破坏当前用友替代路线中的主系统切换。

## 11. 暂不建设

以下内容只因“平台看起来应该有”而建设，当前均不进入计划：

- 任意第三方代码插件市场。
- 通用低代码页面和万能单据引擎。
- 没有客户授权体系的自动营销。
- 没有仓库作业证据的复杂 WMS 算法。
- 没有完整会计政策的通用财务产品。
- 为尚不存在的规模提前拆分大量微服务。
