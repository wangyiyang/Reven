# 产品策略：定位、MVP 与分期路线

> 版本：v1.0
> 日期：2026-07-19
> 依据：`workspace-evidence.md`（本文所有事实性断言的证据出处）
> 标记约定：【事实】【推断】【建议】【未知】

## 1. 执行摘要

1. **根本问题**：业务事实没有系统承载——用友单据可被事后修改且无审计，经营口径散落在 18+ 个复制脚本中互相矛盾，每次纠错只产生下一个一次性脚本。真实价值（可信的日报/库存/提成加工能力）已被验证存在，但它寄生在不可维护的形态上。
2. **第一阶段定位：经营平台，不是报表平台，也不是完整 ERP**。报表平台解决不了事实可变性和规则漂移；完整 ERP 没有任何采购/财务数据证据支撑。
3. **MVP 三件事**：①弹性导入与可信数据层（原始不可变+血缘）；②销售/商品/库存/目标四个证据充分领域的标准模型与指标语义层；③纠错工作台（人）+ 只读 Agent。提成只做试算与未匹配治理，不做结算闭环。
4. 对不固定 Excel 的答案：**≤10 个版本化映射模板 + 原始层 + 纠错工作台**，而非高通用性解析引擎——实测销货表只有 5 种结构。
5. 路线分五期，每期有可验证退出条件；CRM/WMS/SRM/OMS/售后严格留在远期 backlog，不污染 MVP。

## 2. 问题 1：真实业务价值与根本问题

### 2.1 真实价值【事实】

- Agent 每天把"用友导出 Excel → 经营判断"的加工时间压缩到分钟级：三连日报、负卖/零可用预警、滞销机逐人明细、目标完成率、月度提成。
- 独立对账证明其核心加工**可以是对的**：6.9 日报、6.12 库存预警、5 月提成（2,059 行）均 100% 复算通过。
- 这些口径（净额、二人组拆分、空调套数、残机库、滞销清单）是用户与 Agent 三个月、50+ 次纠错磨合出的**真实业务知识**，是平台最值钱的资产。

### 2.2 根本问题（按因果排序）【事实+推断】

1. **事实不可信**：用友单据事后可改（7.4 改部门、7.5 改金额），历史报表与系统背离，无审计、无版本。一切下游指标随之不可信。
2. **规则无单一事实源**：D 组 5 版并存、滞销清单 5 版并存、完成率口径 5 处错误实现、7 月报告错用 6 月目标。每次规则变更只能改 N 个脚本，改一处漏一片（已复发 3 次以上）。
3. **知识无法沉淀**：50+ 次纠错的经验存在日记和记忆里，不在代码和数据里；最新 v2 skill 仍犯净额规则错误。
4. **数据输入靠人肉+运气**：飞书发文件、Agent 猜文件名，同名多版本、文件名日期不符已致 ≥4 次出数错误。
5. **安全裸奔**：明文凭据 3 类、客户 PII 50+ 文件、无 git 保护。

## 3. 问题 2：第一阶段做报表平台、经营平台还是完整 ERP？

**结论：经营平台。**【建议】

| 选项 | 判定 | 理由（证据） |
|---|---|---|
| 报表平台 | 不够 | 只读展示不解决事实可变性（§2.2-1）和规则漂移（§2.2-2）；且用户痛点不止"看数"，还有纠错、分摊、未匹配治理等**操作闭环**（提成表 1,139 行未匹配、滞销机逐人任务） |
| 完整 ERP | 不能 | 无采购/供应商/应收应付/总账任何数据样本（evidence §3.1）；用友版本未知；提成底表都不在 workspace。无证据设计即臆造 |
| 经营平台 | 正确 | 销售/商品/库存/目标四域证据充分且高频（74+19 个文件、每日使用）；先成为"事实与规则的可信层 + 异常处理工作台"，再谈接管记账 |

经营平台与报表平台的本质区别：平台**拥有**标准化业务事实和版本化规则（写路径），报表平台只读。拥有事实，才有后来的记账主权。

## 4. 产品定位与 MVP

### 4.1 定位【建议】

> 面向多门店家电经销商的 AI 原生经营平台：吸收任意格式 Excel，沉淀可信业务事实与版本化规则，用工作台和 Agent 完成经营查询、诊断、异常处理与协作；按域逐步接管用友。

### 4.2 MVP 范围【建议】

| 域 | MVP 能力 | 证据支撑 |
|---|---|---|
| 数据接入 | 文件上传、哈希+单据+明细三层去重、模板识别、映射、纠错、对账、批次血缘 | 109 个真实 Excel、5 种销货结构、9 组重复、1 损坏 |
| 商品主数据 | SKU/名称/型号/品牌/品类/别名/UPC/序列号映射；一品多码治理 | 编码跨表不一致、名称即主键、5.3% TSV 匹配率 |
| 销售 | 销售/退货/换机事实、**来源版本链**（事后改单显式化）、二人组/三人组分摊、空调套数 | 退货月均 ~¥20-36 万、同单正负 80-105 单/月、事后改单实证 |
| 库存 | 快照、可用量、在途、负卖/零可用预警、残机库、滞销清单（版本化） | 6.12 预警复算一致、3 号库规则、60 款清单 |
| 目标 | 月目标版本、累计完成率（禁用单日口径） | 6/7 月目标值、口径错误实证 |
| 提成 | **试算**（10%/2%/计件规则已逆向）、未匹配商品治理队列、底表管理 | 规则逆向 + 1,139 行未匹配 + 底表缺失 |
| Agent | 只读：指标查询、异常解释、证据引用；草稿：滞销任务分配 | 见 target-architecture §6 |
| 治理 | 凭据轮换、PII 脱敏、审计、黄金样本回归 | 安全清单 |

### 4.3 明确非目标（MVP 不做）【建议】

- **提成结算闭环**（试算→对账→审批→锁定）：底表权威来源未知、32% 未匹配，先治理数据再谈结算。与 docs spec 分歧点。
- 财务总账/应收应付/税务；采购订单/供应商结算；售后/配送安装；CRM/会员/营销；POS。
- Agent 写操作（调价、库存调整、结算）。
- 微服务拆分；任意第三方插件；万能单据引擎。

## 5. 问题 3：不强迫统一 Excel，如何建可信数据层？

**结论：可信性来自"原始不可变 + 版本化模板 + 确定性对账 + 事后变更显式化"，不来自格式统一。**【建议】

四层机制（详细状态机见 docs/flexible-excel-import-design.md，本文档修正其规模假设）：

1. **原始层不可变**：文件哈希入对象存储，raw_row 原样留痕；纠错产生修正记录，不覆盖原值。
2. **模板版本化**：按结构指纹（字段集合+表头层级+列类型）匹配模板。实测只需 ≤10 个模板覆盖存量（销货 5 种 + 现存 3 种 + 序列号/提成各 1）；新格式走"Agent 建议映射 → 人工确认 → 发布新模板版本"，**确认后的映射沉淀为模板，不再产生新脚本**——这直接根治"18 个三连变体"。
3. **提交前确定性对账**：原始净额=标准单据净额=分摊合计；不一致必须由规则修复或有权限者显式接受，Agent 不得文字放行。
4. **来源版本链**（对 docs 设计的增补）：同一单据编号在新批次中内容变化时，生成单据新版本并保留旧版本与差异——因为用友事后改单是**常态**（7.4/7.5 实证），upsert 会静默丢失历史。

## 6. 问题 4：平台表格的职责边界

**平台表格 = 导入纠错工作台 + 异常处理队列，不是数据存储范式。**【建议】

### 6.1 平台表格承担的职责

- 导入预览三层视图：原始行（只读）/ 标准化预览（可建修正）/ 正式结果（只读）。
- 行级纠错与批量修正（先显示影响行数/金额，确认后应用，全程审计）。
- 异常队列：未匹配商品、未知业务员、分摊不平、对账差异——人在这里处理，Agent 只给建议。
- 模板确认与发布入口。

### 6.2 不能放进"万能动态表"的数据

- 正式业务事实（销售单、库存流水、提成结果）——必须落在强类型领域表，有约束、有状态机。
- 规则（分组、目标、滞销清单、提成比例）——版本化规则表，不是单元格。
- 任何"先存进 JSONB 再说"的重要流程字段——docs 原则正确：**重要字段必须提升为正式模型**。
- 理由【推断】：本 workspace 的全部灾难（口径漂移、静默错误、无法重算）都源于"灵活存储、刚性缺失"；动态表只是把同一问题搬进数据库。

## 7. 问题 13：分期路线（进入/退出条件）

| 期 | 内容 | 进入条件 | 退出条件（可验证） |
|---|---|---|---|
| 0 安全与基线 | 凭据轮换（3 类明文）、.gitignore/secret scan、PII 脱敏策略、黄金样本集 | 立项 | 无明文凭据；≥30 个黄金案例（含净额/二人组/空调套数/负卖/事后改单）全部有业务确认期望值 |
| 1 可信数据层 | 弹性导入（销货+现存两类）、三层去重、版本链、对账 | 期 0 完成 | 历史文件批量导入：重复导入=0；原始/标准/分摊三层金额差=0；5 种销货结构全识别 |
| 2 经营工作台 | 销售/库存/目标指标语义层、异常队列、滞销清单版本化、提成试算+未匹配治理 | 期 1 完成 | 用户连续 2 周不用临时脚本出日报；完成率等关键指标与手工口径对账一致；提成未匹配清单可闭环处理 |
| 3 只读 Agent | 指标查询、异常解释、证据引用、评测集 | 期 2 完成 | 离线评测集（≥50 问）通过率达标；数字回答 100% 带指标版本+批次证据 |
| 4 操作闭环 | 滞销任务、分摊修正、提成试算审批、草稿→审批→执行→审计 | 期 3 完成 | ≥1 条业务线从发现到处理全程留痕；高风险动作 100% 过审批 |
| 5+ 接管用友 | 见 migration-roadmap.md | 用友盘点完成（版本/接口/模块确认） | 见该文档 §退出门槛 |

## 8. 问题 14：缺失样本、用友信息与关键决策

### 8.1 必须补充的业务样本【未知→需采集】

1. 提成"底表"（进价/定价/计件标准）原始文件及其维护流程——**决定提成域能否做结算**。
2. 采购/进货单、供应商、付款样本——决定采购域设计。
3. 应收应付/收付款/凭证样本——决定财务边界。
4. 完整的换机、残机处理、赠品/返利单据样本。
5. 批发部门的销货单——当前 74 个文件几乎全是零售（1,497/1,497 行属零售部门）。
6. 6.11 销货单、原始 0706 文件——闭环两处对账缺口。

### 8.2 必须确认的用友信息

产品名称与版本、部署方式、已购模块、接口/只读库能力、导出模板为何漂移（5 种表头是谁在改）、单据事后修改的权限与频率。

### 8.3 需要用户拍板的关键决策

1. **单租户产品还是 SaaS**：决定多租户投入时点（建议：模型留 tenant_id，RLS 延后）。
2. **D 组名单与滞销清单的权威维护人**：决定规则治理的责任角色。
3. **提成底表谁来维护、放在哪里**：决定提成域从"试算"升级为"结算"的时间点。
4. **平台接管后数据发送人的工作流如何变化**：人肉数据管道是第一个被平台替代的环节，涉及人的安排。
5. **替代终点**：经营系统替代（财务留用友）还是完整 ERP 替代——两者投入差一个数量级。
