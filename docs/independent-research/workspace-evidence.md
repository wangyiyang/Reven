## 1. 执行摘要

1. workspace 是一家拥有两个门店的家电经销商（身份已匿名）围绕用友进销存 Excel 导出形成的"影子经营系统"：AI Agent 每日用一次性 Python 脚本加工销货单明细、现存量查询等报表，产出销售日报、滞销机分析、空调分析、库存预警、目标完成率和工资提成。【事实】
2. 真实业务价值已被验证：6.9 日报、6.12 库存预警与原始数据独立对账**完全一致**；5 月提成表 2,059 行已匹配行公式 100% 复算通过。Agent 的加工能力真实存在且可复现。【事实】
3. 根本问题不是"算不对"，而是：**事实可被事后篡改而无审计**（7.4/7.5 两次日报与重导数据的差异均源于事后改部门、改金额、补录退货）、**规则无单一事实源且严重漂移**（D 组名单 5 个版本并存；7 月 4 日报告错用 6 月目标）、**最新 v2 skill 本身仍有已证实的口径错误**（过滤负金额，违背净额规则）。【事实】
4. 数据资产：109 个 Excel + 5 个 TSV，覆盖 2026-05-01 ~ 2026-07-18。销货单明细表存在 **5 种**表头结构、现存量查询 **3 种**（docs 称"62 种签名"系高估，见交叉评审）。9 组 MD5 完全重复文件、1 个损坏文件、合计行/页脚混入数据区、文件名与内容日期不符多发。【事实】
5. 提成规则已从 `5月工资提成计算表.xlsx` 完整逆向：计件提成（底表×数量）+ 利润提成（(调整后金额−底表定价×数量)×10%）+ 小家电提成（金额×2%）；但 32% 行未匹配底表、179 个商品无进价依据，"底表"本体不在 workspace。【事实+未知】
6. 京东 B2B 数据（279 订单行）与门店销售体系匹配率仅约 5%，不能作为门店商品/价格主数据来源；UPC 非唯一、型号缺失 53%。【事实】
7. 高危安全问题：明文京东账号密码（memory 与日记各一处）、明文飞书 app_secret（2 个下载脚本）、明文 LLM_API_KEY（memory_consolidation env）、50+ 文件含客户手机号/住址。【事实，仅报位置】

### 2.2 核心业务流程口径【事实】

- **销售/退货/换机**：销货单正数=销售、负数=退货，同客户同业务员同存货正负相抵按净额计业绩；严禁先过滤退货再求和。6.1-6.23 退货 207 行/-¥358,076.85；7.1-7.15 退货 137 行/-¥199,302.35。显式"换机"备注仅 1 例（LS20260620014），换机主要靠同单正负并存模式推断（6 月 105 单）。
- **组合销售（二人组/三人组）**：业务员列写"二人组/三人组"，备注写分成（"天猫 韩丽梅11500 解贝贝12800"），日报按备注金额比例拆分；滞销机台数按人头平分（0.5 台合法）——**销售与滞销是两套刻意的拆分口径**（v1/v2 SKILL.md 对比表证实）。
- **空调**：内机+外机一套算 1 台，外机行不单独计数；柜挂机按型号正则判定（各脚本实现漂移）。
- **库存**：以"现存量查询"为准，关键字段是**可用量**（≠现存量）；负卖须结合采购在途判断；同型号跨 1/2 号库合并；3 号残机库单独统计。
- **滞销机**：不是动态阈值判定，而是**用户人工维护的静态型号清单**（4 月 38 款 → 5 月 57 款 → 7.9 版 60 款，`skills/daily-triple-report-v2/models.md`），只看台数不看金额，清单外型号不得计入。
- **目标**：按组月度销售额目标（6 月 A/B/C 各 ¥1,473,724、D ¥556,360；7 月 A/B/C 各 ¥1,146,908、D ¥432,980），完成率=组累计净额÷月目标。
- **提成**：见 §5。
- **序列号**：独立序列号跟踪表（10,064 个唯一序列号、11,182 事件行）；销售明细表本身无序列号字段。

### 2.3 编码体系【事实】

- 存货编码纯数字（如 010404336），**同一商品在不同用友报表间编码体系不一致**（库存状况表 vs 出入库流水），跨表只能按**存货名称**关联。
- 存货名称是事实主键，内嵌品牌+品类+型号+颜色；存在一品多码。
- UPC 仅见于京东 B2B 数据，未与用友存货档案打通。
- workspace 内无正式型号映射表，型号提取靠各脚本私有正则，有误匹配事故史（B1201Bi1 vs B1201B 等）。

- 销货单明细表 **5 种表头**：A（31 文件，16 列，重复"客户备注"列）；B（30 文件，17 列，含单据状态/赠品）；C（6 文件，有含税金额/最低零售价、**无"金额"列**）；D（1 文件，18 列透视式）；E（1 文件，表头在第 7 行）。
- 现存量查询 **3 种表头**：简版 12 列 / 全版 24+ 列双层表头 / 混合版缺仓库编码。
- 推论：格式种类有限且可按结构指纹聚类，模板化导入可行；但漂移持续发生（6.16 前后从 B 切到 A），模板必须版本化。【推断】

### 3.3 数据质量【事实】

- 9 组 MD5 完全重复文件（含跨根目录/downloads 重复）；1 个损坏文件（`downloads/销货单明细表7.1-7.13.xlsx`，9 字节，内容="Not Found" 错误页）。

- 合计行混入数据区（如 `销货单明细表6.1-6.28.xlsx` 末行合计 数量2170/金额3,994,235.61）；"第1页/共1页"页脚行混入。

## 6. 代码与规则诊断

### 6.1 重复与漂移【事实】

- 38 个脚本中约 18 个是同一"三连报告"的按日期复制变体；`parse_note` 变体 ≥10 个，品牌/型号提取函数变体各 ≥8 个。
- **D 组名单 5 个版本并存**：`['朱盈欣']`、`['朱盈欣','崔凤存']`、`[朱盈欣,李娜,崔凤存,田智慧]`、7 人版、config.json 14 人版；`stale_analysis.py:273` 的 B 组只有 2 人。
- **v1/v2 skill 互相矛盾**：v1 SKILL.md 把徐玉莲归 D 组，v2 config.json 归 B 组。
- **已证实的错误输出**：`sanlian_0704.py:38` 在 7 月 4 日报告中仍用 6 月目标算"7 月完成率"（:148-156）。
- **完成率口径普遍错误**：多数脚本只有单日数据却输出"单日÷月目标"为完成率（`analysis_0620.py:186`、`_triple_612.py:148` 等 5 处）；仅 3 个脚本做了真累计。
- 滞销机清单规模漂移：48/51/52/57/60 五个版本；`sanlian_0704.py:368` 引用的 models.md 路径在本 workspace 不存在。
- 空调 RF 系列归类在"商用/大口径/大功率/柜机"间漂移；净可用公式两版不一致；价格段两套并存。
- 脚本全部为 Linux 容器 `/root/.openclaw/` 绝对路径，本地不可运行；`_triple_report_611.py:372` 残留 `PYEOF` 语法错误；2 个下载脚本字面损坏。

### 6.2 数据源链路【事实】

飞书群消息附件 → 飞书 OpenAPI 下载 → pandas 读 Excel → 文本报告发回飞书。输入路径模式 5 种并存，靠 Agent 每次现选文件——同名文件多版本、文件名日期不符直接导致选错输入（历史已发生 ≥4 次）。

## 9. 与 docs/ 的交叉评审（阶段二）

### 9.1 得到证据支持的结论

- "影子业务系统"定性、四大缺失基础（数据模型/规则治理/弹性导入/安全治理）——与 §1-§8 全部吻合。

- "v2 不能作为成熟内核直接迁移"——实测复核成立（§4.3）。
- 黄金样本策略与"旧脚本输出仅作参考"——被 7.4/7.5 对账和 sanlian_0704 用错目标两项证据强化。

### 9.2 不准确或证据不足处

1. **"销售类 62 种、库存类 13 种表头签名"高估**：实际销货单明细表为 5 种结构、现存量查询 3 种（§3.2）。"62 种"疑为把含日期/参数的标题行计入签名。后果：会夸大导入层复杂度，诱发过度设计；真实情况是 ≤10 个模板即可覆盖存量。
2. **docs 未发现"事后改单"问题**：7.4/7.5 差异证明用友单据在日报发出后会被修改（§4.1），这比"格式不固定"更根本——它决定了必须做**不可变快照+事后变更显式化**，仅做"导入幂等"不够。docs 的数据模型未覆盖"同一单据的来源版本演进"。
3. **docs 对提成只说"规则需输入"**：实际规则已从提成表完全逆向（§5，10%/2%/计件底表），可直接作为规则引擎首批版本化规则与黄金测试；真正的缺口是"底表"权威来源，而非规则未知。
4. **docs 高估京东 B2B 数据价值**：实测匹配率 5.3%（§7），它只能证明"存在京东进货渠道"，不能支撑商品价格主数据建设。
5. **滞销金额缺口未被 docs 识别**：无成本数据，滞销只能看台数——补货/处置决策的金额化需要成本底表，这是影响 MVP 范围的真实约束。
6. **"完成率=单日÷月目标"的普遍性**（5 处脚本）和 sanlian_0704 错用月份目标，docs 未点名；这是"指标语义层"必要性的最强实证，应写入证据链。

### 9.3 docs 遗漏的重要问题

- **事实可变性**：用友单据事后可改且无审计（§4.1）→ 需要单据级版本/冲销模型，而非 upsert。
- **退货/换机规模**（月均 ~¥20-36 万、同单正负并存每月 80-105 单）——换机是高频流程但无单据类型承载，平台必须把它建成一等公民。
- **凭证泄露的具体位置**（§8）——docs 只说"应轮换"，未给出轮换清单。
- **另一业务 Agent 的存在**——多 Agent 无协调写同一业务口径的风险。【未知：其职责与关系】
- **数据发送人（非业务员）角色**——数据管道中的人肉环节，导入平台化后其工作流需重新设计。

### 9.4 过度/过早设计处

- spec 将 LangGraph 写入技术基线（§6.1）属过早绑定：审批等待本质是 DB 状态机，先用确定性工作流，确需暂停/恢复编排再引入（详见 target-architecture.md §7）。
- MVP 即内置多租户全套（RLS 等）成本不低；单租户先行、数据模型保留 tenant_id 即可，RLS 可延后。
- `future-product-roadmap.md` 的 CRM/WMS/SRM/OMS 分层合理，但"营销自动化/会员"无任何 workspace 证据，应严格留在 backlog。

### 9.5 独立建议与 docs 的主要分歧

| 议题 | docs | 本调研 |
|---|---|---|
| 第一阶段形态 | "经营平台"，范围含目标/提成/Agent | 一致，但**提成结算应从 MVP 后移**：底表缺失+32% 未匹配，先做"提成试算与未匹配治理"，不做结算闭环 |
| 导入层 | 按"62 种签名"设计高通用性 | 按 ≤10 个真实模板聚类设计，指纹+版本化即可，避免过度通用 |
