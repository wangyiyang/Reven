## 1. 文档目的

本文把产品愿景拆成 5 个可以独立验收的阶段。上一阶段退出条件未通过，不进入下一阶段。

| 阶段 | 名称 | 核心结果 |
|---|---|---|
| Phase 0 | 安全与事实基线 | 有可信期望值，敏感风险受控 |
| Phase 1 | 可信数据层 | 不固定 Excel 可以稳定进入标准事实 |
| Phase 2 | 经营工作台 | 核心日报和异常不再依赖临时脚本 |
| Phase 3 | 智能协作闭环 | Agent 可查、可解释、可生成受控草稿 |
| Phase 4 | 用友渐进接管 | 建立接管机制并完成首个销售域切换 |

Phase 4 之后的库存、采购、财务接管，以及 CRM、售后、WMS、SRM 等模块，需要基于届时证据另立 PRD。

## 2. 产品概述

### 2.1 产品定位

面向多门店家电经销商的 AI 原生经营平台：吸收持续变化的 Excel，沉淀可信业务事实和版本化规则，通过工作台与 Agent 完成经营查询、诊断、纠错、审批和协作，并按业务域逐步替代用友。

### 2.2 核心问题

1. 用友导出后的数据依赖人工传递、选文件和运行脚本。
2. 同一用友单据可能事后改变，历史报告无法追溯差异。
3. 人员、滞销、目标、分摊等规则多版本并存。
4. 报表结果散落在飞书文本和 Excel 中，无法形成处理闭环。
5. Agent 缺少可信工具和权限边界，现有自动化不可审计。
6. 凭据、客户个人信息和附件指令存在安全风险。

### 2.3 产品目标

- 所有核心经营数字可追溯到文件、原始行、单据版本和规则版本。
- 格式变化通过版本化模板和纠错工作台吸收，不再产生日期脚本。
- 页面、飞书和 Agent 使用统一指标语义。
- 异常能够被发现、指派、处理和关闭。
- 每个用友接管领域有唯一记账主系统和可验证切换门槛。

### 2.4 当前非目标

- 一次性替换完整用友。
- 正式提成结算和工资发放。
- 采购、应收应付、总账、税务、售后和 CRM。
- Agent 直接修改正式事实或执行任意 SQL。
- 微服务、任意插件市场和通用低代码平台。

## 4. 全局产品原则

### 4.1 事实与版本

- 原始文件和原始行不可变。
- 用户纠错创建修正记录，不覆盖原值。
- 同编号单据内容变化创建新来源版本。
- 已发布指标引用固定事实范围和规则版本。
- 已确认业务事实只能通过新版本、冲销或更正改变。

### 4.2 计算与 Agent

- 金额使用 Decimal 和显式舍入规则。
- 销售、库存、提成和指标均由确定性服务计算。
- Agent 只通过已登记工具访问数据。
- Agent 输出数字必须携带时间、组织、指标版本和来源证据。
- 高风险动作统一经过草稿、校验、审批、执行和审计。

### 4.3 范围与扩展

- 首发按单租户实现，所有业务实体预留 `tenant_id`。
- 业务模块拥有自己的表和状态，禁止跨模块直接写表。
- 跨模块使用公开应用接口或版本化领域事件。
- 新模块必须有真实流程、真实样本、明确事实所有权和退出条件。

## 5. 核心用户旅程

### 5.1 每日导入

用户上传销货或库存 Excel，系统识别模板并执行标准化。已知格式自动进入对账；未知格式展示映射建议。用户只处理阻断异常，确认后发布正式数据和日报。

### 5.2 事后改单

同一单据出现在新文件中但内容变化，系统展示旧值、新值、金额影响和来源批次。用户确认后创建新单据版本，历史指标保留，当前指标按新版本重算。

### 5.3 经营异常

工作台展示导入、销售、库存、目标和提成异常。责任人查看证据、处理问题并关闭任务，经营者能看到处理状态和影响。

### 5.4 智能查询

用户询问“昨天空调为什么下降”，Agent 调用指标和明细工具，返回变化、主要影响项和可下钻证据。数据不足时明确说明缺失，不猜测原因。

### 5.5 用友接管

平台先影子读取并独立计算销售事实，连续对账达标后切换读流量，再在受控窗口切换主写权；稳定期通过后，用友销售入口转为只读。

- 用友信息和提成底表问题至少有明确责任人与获取计划。

| P1-BATCH-01 | 批次具有状态机、上传者、来源、模板和代码版本 | P0 |

### 7.5 退出条件

- 现有可读取销货/库存文件全部进入预览；损坏文件被正确拒绝。
- 5 种销货和 3 种库存结构全部自动识别。
- 同一文件或单据重复导入不产生重复事实。
- 原始净金额、标准单据金额和分摊金额差异为零。
- 未知业务员、伪人名和未匹配商品不会静默进入正式数据。
- 已知事后改单样本全部形成来源版本链和可解释差异。
- 黄金案例全部通过自动回归。

## 8. Phase 2：经营工作台

### 8.1 阶段目标

用统一指标和异常工作台替代临时三连脚本，建立高频经营入口。

### 8.2 工作台需求

| ID | 需求 | 优先级 |
|---|---|---:|
| P2-WB-01 | 首屏按优先级展示待处理异常，不以图表为主 | P0 |
| P2-WB-02 | 支持按门店、组、人员、日期、品类和状态过滤 | P0 |
| P2-WB-03 | 异常可指派、评论、处理、关闭和重新打开 | P1 |
| P2-DRILL-01 | 任意数字和异常可下钻到规则、单据和原始行 | P0 |
| P2-FS-01 | 飞书返回导入状态、日报摘要和高优先级异常 | P1 |

### 8.3 业务能力需求

| ID | 需求 | 优先级 |
|---|---|---:|
| P2-SAL-01 | 销售净额、退货、分组/个人业绩和分摊明细 | P0 |
| P2-AC-01 | 空调内机净套数、品牌、柜挂机、型号和价格段 | P0 |
| P2-INV-01 | 现存、可用、在途、负卖、零可用和残机预警 | P0 |
| P2-STG-01 | 人工滞销清单版本化、动销和责任人任务 | P0 |
| P2-TGT-01 | 月目标版本、累计完成率、进度差和日均缺口 | P0 |
| P2-COM-01 | 提成试算、底表版本和未匹配商品队列 | P1 |
| P2-COM-02 | 未匹配项不得默认视为提成零且静默通过 | P0 |

### 8.4 指标语义需求

- 页面、飞书和未来 Agent 只能调用指标服务。
- 每个指标定义时间、维度、过滤、退货/赠品/外机口径和版本。
- 完成率只允许使用累计净额，禁止单日金额除月目标。
- 滞销指标必须引用清单版本；无成本时不得输出滞销金额。
- 指标重算产生新结果版本，不覆盖已发布历史。

### 8.5 退出条件

- 用户连续两周无需临时脚本生成核心日报。
- 销售、空调、库存、滞销和目标黄金案例全部一致。
- 所有工作台数字可下钻到证据。
- 规则只维护一处，发布前自动执行黄金回归。
- 提成未匹配项可被发现、分派和持续减少，但不进入正式结算。

## 9. Phase 3：智能协作闭环

### 9.1 阶段目标

让用户用自然语言查询可信指标、理解异常并生成受控操作草稿，至少形成一条完整处理闭环。

### 9.2 Agent 需求

| ID | 需求 | 优先级 |
|---|---|---:|
| P3-AGT-01 | 支持经营指标查询、对比、排名和下钻 | P0 |
| P3-AGT-02 | 回答包含查询范围、指标/规则版本和证据链接 | P0 |
| P3-AGT-03 | 数据或口径不足时明确拒答或请求澄清 | P0 |
| P3-AGT-04 | 工具执行权限与当前用户数据范围一致 | P0 |
| P3-RAG-01 | RAG 仅检索规则、说明书和历史纠错等文档 | P1 |
| P3-INJ-01 | 附件、备注和文档中的指令不能改变 Agent 策略 | P0 |

MVP 直接使用模型 SDK、工具目录和数据库状态机，不把 LangChain/LangGraph 作为前置依赖。

### 9.3 操作闭环需求

| ID | 需求 | 优先级 |
|---|---|---:|
| P3-ACT-01 | Agent 可生成滞销任务、分摊修正等操作草稿 | P0 |
| P3-ACT-02 | 草稿显示规则、参数、影响范围和风险等级 | P0 |
| P3-APP-01 | 高风险动作经角色审批后由确定性服务执行 | P0 |
| P3-AUD-01 | 发起、建议、确认、执行和结果全程审计 | P0 |
| P3-NOT-01 | 飞书通知责任人，并允许查看/确认低风险任务 | P1 |

首条闭环建议选择“滞销任务”：发现滞销型号、建议责任组、人工确认、指派、跟进、完成、复盘。它不涉及财务过账，风险低且现有证据充分。

### 9.4 评测与退出条件

- 建立不少于 50 个来自真实纠错史的问题集。
- 数字回答与指标层一致率 100%，并全部携带证据。
- Prompt Injection、越权、任意 SQL 和直接写事实测试全部被拒绝。
- 至少一条业务线从发现问题到处理完成全程留痕。
- 高风险操作 100% 经过权限校验和人工确认。
- 模型、Prompt、工具或规则变化前自动执行离线回归。

## 10. Phase 4：用友渐进接管

### 10.1 阶段目标

建立可重复的模块接管机制，并优先完成证据最充分的销售域切换。库存、采购和财务继续沿用该机制，但不属于本阶段交付承诺。

### 10.2 前置条件

- 用友产品、版本、模块、接口和修改权限已完成盘点。
- Phase 1-3 全部通过退出条件。
- 销售单、退货、换机、分摊和未完成单据范围已确认。
- 销售开单到撤销更正的实际流程及其库存、收款、财务依赖已经业务签字。
- 业务负责人、系统负责人和回退责任人已确定。

### 10.3 接管需求

| ID | 需求 | 优先级 |
|---|---|---:|
| P4-ACL-01 | 防腐层把用友字段/状态转换为平台标准命令和事件 | P0 |
| P4-SAL-01 | 支持销售、退货、换机的草稿、确认、撤销和更正状态机 | P0 |
| P4-SAL-02 | 平台提供可替代用友高频开单的录入、校验和查询入口 | P0 |
| P4-INT-01 | 已确认销售单以幂等接口同步尚未迁移的库存和财务域 | P0 |
| P4-SOR-01 | 按租户和领域维护唯一 `owner_system` | P0 |
| P4-SOR-02 | 非主权系统写请求必须被拒绝并审计 | P0 |
| P4-SHD-01 | 支持影子读取、独立计算和逐日自动对账 | P0 |
| P4-CUT-01 | 切换窗口支持冻结、期初、增量、切权和验证 | P0 |
| P4-RBK-01 | 定义回退窗口、补偿方式并完成演练 | P0 |
| P4-ARC-01 | 切换完成后用友销售域只读，历史仍可检索导出 | P0 |
| P4-OBS-01 | 监控同步延迟、差异、失败、拒绝写入和切换状态 | P0 |

### 10.4 状态要求

```text
已盘点 -> 已映射 -> 影子读取 -> 影子计算 -> 对账通过
       -> 切换读 -> 切换写 -> 稳定期 -> 平台主权 -> 用友归档
```

影子阶段只计算不产生外部效力；临时双写仅允许存在于受控切换窗口，并必须自动对账。

### 10.5 退出条件

- 销售域连续至少两周数量和金额差异为零，或差异全部签批。
- 任一时点销售域只有一个 `owner_system`。
- 切换窗口外双写为零，非主权写请求拦截率 100%。
- 高频开单及退货、换机、撤销、更正流程可在平台独立完成。
- 未迁移库存和财务域收到的销售结果与平台单据逐笔对账通过。
- 销售、退货、换机和分摊的异常、撤销及更正流程验收通过。
- 回退演练、备份恢复和历史归档查询通过。
- 用友销售入口停止新增，平台成为销售域唯一主写系统。

## 11. 全局非功能需求

### 11.1 安全与隐私

- 所有请求携带身份、租户和数据范围。
- 客户电话、地址默认脱敏，查看原值需要单独权限并审计。
- 原文件加密存储，下载使用短时授权。
- 密钥不得进入代码、日志、数据库业务表或 Agent 上下文。
- 文件宏、公式外链、嵌入对象和附件指令不得执行。

### 11.2 可靠性与一致性

- 导入提交、业务命令和审批执行必须幂等。
- 模块内部事务强一致；跨模块事件使用 Outbox/Inbox。
- 失败不得产生半批正式事实。
- 所有重算和同步任务支持安全重试。
- 备份恢复目标和业务连续性指标在 Phase 0 结合部署环境冻结。

### 11.3 性能

- Phase 0 记录当前最大文件、导入耗时和高峰并发基线。
- Phase 1 至少通过当前最大可读样本 2 倍规模的导入测试。
- 长任务异步执行，用户能看到进度、失败位置和重试状态。
- 指标查询目标在 Phase 2 根据真实数据量冻结，不提前承诺无证据 SLA。

### 11.4 可观测性

- 统一关联 `request_id`、`import_batch_id`、`business_document_id` 和 `agent_run_id`。
- 记录阶段耗时、异常码、模板命中、人工修正、对账差异和工具调用。
- 日志默认脱敏，禁止记录完整文件正文和客户个人信息。

### 11.5 易用性

- 阻断、确认、警告和通过不能仅用颜色区分。
- 批量操作必须先展示影响范围。
- 移动端负责查看、确认和指派，复杂表格纠错以桌面端为主。
- 错误信息说明发生了什么、影响什么以及下一步动作。

## 13. 依赖与待决策

### 13.1 业务依赖

- D 组等人员归属的权威名单和生效日期。
- 滞销清单与月目标的维护责任人。
- 提成底表、进价、定价和计件标准。
- 完整换机、残机、赠品、返利和批发样本。

### 13.2 系统依赖

- 用友具体版本、数据库/API/导出能力和修改权限。
- 飞书应用权限、事件订阅和身份映射。
- 部署、对象存储、备份和密钥管理环境。

### 13.3 产品决策

1. 首发部署是否只服务当前商家；本 PRD 默认是。
2. 销售域接管后是否仍需向用友财务生成凭证或汇总；待用友盘点。
3. 完整替代终点是否包含总账；不影响 Phase 0-4，但影响后续路线。
4. 提成域何时从试算升级为正式结算；由底表匹配率和财务确认决定。

## 14. 发布治理

- 每阶段开始前确认需求、负责人、输入样本和退出条件。
- 业务规则变更必须经过草稿、黄金回归、审批和定时生效。
- 数据模型和 API 变更需要迁移方案及向后兼容说明。
- 阶段验收由业务、产品和技术共同签字，不能只以“功能已开发”结束。
- 发现影响金额、库存或权限的重大缺陷时停止下一阶段并完成回溯。
