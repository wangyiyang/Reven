# PRD：品牌与发布标准化

> 来源：GitHub Issue [#46](https://github.com/wangyiyang/Reven/issues/46)（关联 Epic [#41](https://github.com/wangyiyang/Reven/issues/41) Notion 退役）

## 目标与用户价值

用户维护一次「翊行代码」品牌资料后，Reven 在博客和微信公众号发布过程中自动应用品牌身份、排版及文末信息，并提供可操作的校验结果，减少重复配置和发布返工。

首版围绕**一个主品牌、单人操作、博客与公众号两个渠道**完成闭环。用户在 Notion 写稿，Reven 把同一份稿件交付为符合品牌要求的渠道产物，只有缺失素材、配置冲突等异常需要用户处理。

效果以每篇稿件的重复录入次数、人工处理步骤和发布返工情况衡量。**实施前记录一篇代表性稿件的现有操作步骤，验收时按同一场景对比**；不以新增表或导入规则数量作为业务成果。

## 已确认事实（代码勘察）

- 发布编排骨干已存在：`PublicationOrchestrator`（server/src/reven/publishing/orchestrator.py）按渠道逐个交付，已成功渠道在重试时跳过（`_channel_finished`），失败分 Transient/Blocked/Permanent 三类。
- 校验已分两级：`validate_candidate`（publishing/validation.py）返回 `errors`（阻塞）+ `warnings`（提醒），封面缺失 `cover_missing` 已是阻塞项——可直接映射「提醒/阻塞」分级模型。
- 微信品牌样式硬编码在 TS 渲染器：`renderer/src/render.ts`（主色 `#00E676`、字体栈等），Python 侧经 `WechatRenderer` 子进程调用 `renderer/dist/cli.mjs`，输入仅 markdown。
- 署名现状来源：微信集成的 `public_config.author`（jobs/preparation_state.py:69）——正是 issue 要消除的重复录入点，需保留为 legacy fallback。
- 博客转换为 Jekyll frontmatter（publishing/blog/converter.py），当前无封面与 OG 字段；博客模板消费方式已验证：`page.cover`（_includes/theme/post-header.html:33-36）、`page.og_image_url`（_includes/header.html:87-88、_layouts/post.html:30-31）、`page.description`、`keywords`。
- 内容快照 `ContentSnapshot`（publishing/snapshot.py）以 markdown + 图片 sha256 + 封面 sha256 计算 `content_hash`；任务幂等锚点为唯一约束 `(article_id, content_hash, target_channels_hash)`（jobs/models.py）。
- 微信预览 `ConfiguredWechatPreview` 从当前快照实时渲染；预览与交付都经同一渲染器，模板应用放在渲染前可天然保证一致。
- 素材存储可复用：`ContentAssetStore` 协议 + 腾讯云 COS 实现（integrations/tencent_cos/store.py），快照素材即以 sha256 + storage_key + public_url 归档。
- Notion 客户端具备 `retrieve_page` / `retrieve_page_markdown`（integrations/notion/client.py），拉取 VI Hub 页面可行。
- 前端：react-router 集中路由（web/src/app.tsx）+ app-shell 导航数组（:45）+ shadcn 风格 ui 组件；设置页模式参照 features/integrations；工作台蓝灰主题规范在 `.trellis/spec/web/frontend/brand-vi.md`（Active）。

详细调研见 `research/backend-publishing-seams.md` 与 `research/frontend-assets-notion.md`；存储结构与集成设计见 `design.md`；执行顺序见 `implement.md`。

## 需求

### R1 四个业务对象

| 对象 | 内容与职责 | 使用方式 |
| --- | --- | --- |
| 品牌档案 | 品牌名、简介、默认署名、handle、官网、Tagline、配色、字体与简短表达风格说明 | 统一维护对外身份，两个渠道的共同来源 |
| 品牌素材 | Logo、头像、二维码、常用图片及其用途、启用状态 | 上传、预览、选择；复用既有资产存储能力 |
| 渠道模板 | 微信排版与文末模块；博客署名、封面及分享卡片（OG）字段映射 | 每渠道先提供一个默认模板，套用品牌档案与选定素材 |
| 发布记录 | 本次正文、品牌版本、渠道模板版本、实际素材及交付结果 | 查看、追溯、使用原配置重试 |

品牌档案表达统一身份；渠道模板负责渠道差异。具体存储结构在 `design.md` 确定。

### R2 日常发布流程

1. 从 Notion 同步稿件，形成内容快照（现有能力）。
2. 使用当前有效品牌档案和目标渠道默认模板，保留稿件已选封面；缺失时提供选择已有素材或上传的入口。
3. 自动套用微信样式、默认署名和文末模块，并准备博客所需的品牌及封面、OG 字段。
4. 提供与实际交付一致的预览和校验结果；问题同时给出原因和处理入口。
5. 沿用现有发布流程交付博客和微信草稿，保存本次使用的配置与素材版本。

约束：
- Notion 继续作为稿件正文权威来源。模板增加的署名、文末模块属于渠道产物，**不回写正文**；稿件已包含相同模块时避免重复追加，无法明确判断的冲突提示用户。
- 博客封面与 OG 字段需与目标博客实际模板消费方式配套验证，不能只写入未被使用的元数据。

### R3 自动完成、提醒与阻塞分级

| 处理方式 | 适用情况 | 行为 |
| --- | --- | --- |
| 自动完成 | 套用排版、补默认署名、插入已配置的文末模块 | 使用确定的配置生成产物，预览可见 |
| 提醒并允许继续 | 素材比例偏离推荐值、署名或文末模块存在需人工判断的冲突 | 说明具体问题并给出处理入口 |
| 阻止发布 | 必需封面缺失、素材不可读取、目标渠道必填项或硬性要求不满足 | 阻止交付，修复后可重新校验 |

渠道接口约束由渠道适配层负责；品牌偏好由品牌档案和模板负责。文风、审美等主观判断保留为说明或人工检查建议，**首版不建设 AI 自动审查**，不作为强制阻塞条件。

### R4 页面入口

- 低频维护：「品牌与发布设置」页，集中维护品牌资料、基础素材和两个渠道的默认模板。
- 高频操作：稿件详情中展示本次模板、素材、预览、校验问题与处理入口。
- 发布历史：查看实际使用的版本和交付结果。
- 未来首页聚合待处理异常；本议题**不新增**通用任务或工作流系统。

### R5 版本与重试规则

- 品牌资料和渠道模板支持草稿修改，启用后形成可追溯版本。
- 同一次发布的博客与微信使用同一品牌版本，各自绑定明确的渠道模板及素材版本。
- 预览与实际交付绑定同一组内容和配置；正文、品牌、模板或素材变化时，旧预览明确失效，重新生成后再使用。
- 发布开始后冻结实际配置与素材。失败渠道重试继续使用原版本，已成功渠道不重复交付。
- 品牌升级仅影响后续新发布，不自动重发历史稿件，不改变已冻结任务。
- 历史稿件主动使用新版时，通过明确的重新生成及交付操作处理；实现时必须区分「重试原任务」和「使用新版重新生成」的幂等语义。
- 被历史发布引用的版本和素材需要保留，不能因默认配置更新而失去追溯依据。

### R6 Notion 迁移

- 将 VI Hub（Notion page `67477fcdc2ce40c2ab93a52976f08318`）有效资料一次性导入为**待核对草稿**，保留来源标识和迁移结果。
- 原 VI v2.1 中的碳黑、冷白、终端绿、`{翊}` 几何 Logo、handle `wangyiyang` 等作为待核对的初始资料，**不硬编码为永久业务约束**。
- 迁移支持 dry-run、重复执行不重复创建、条目与素材计数核对；不可导入项明确列出原因。
- 核对并验证实际发布可用后，按 #41 迁移流程将 Notion 来源归档为历史；不删除原资料，不在导入完成时直接切换权威来源。
- AI 生图方法、Prompt Kit 和人工检查方法复用现有 SOP/话术模块，品牌及发布配置只引用实际需要的信息与最终素材。

### R7 兼容性与范围约束

- 复用现有内容快照、素材存储、校验及交付链路。
- 现有稿件与历史任务保持可查看、可重试，**不要求先批量回填新品牌配置才能工作**。
- 品牌配置控制对外产物，Reven 工作台自身的蓝灰主题保持独立。
- 博客继续通过 GitHub Flow 发布；公众号继续仅生成草稿，公开发布由用户在公众号平台确认。

## 验收标准（对应 issue 首版验收）

- [ ] AC1 完成一个品牌档案及博客、微信各一个默认模板的配置；用户无需逐篇重复录入品牌名、署名、handle 和固定文末信息。
- [ ] AC2 修改并启用默认署名后，后续新发布的两个渠道均应用更新；历史记录与已冻结任务保持原版本。
- [ ] AC3 一篇代表性稿件完成微信排版、文末模块和博客品牌字段配置，已有署名或文末模块不会被重复追加。
- [ ] AC4 博客实际页面的封面与 OG 输出符合所选模板映射，微信草稿使用正确封面与排版。
- [ ] AC5 预览与实际交付使用同一组内容和配置；内容或配置变化后旧预览明确失效。
- [ ] AC6 缺失必需封面、素材不可读取或渠道硬性约束不满足时明确阻塞，并提供原因和处理入口；修复后能够重新校验。
- [ ] AC7 推荐性问题可提醒后继续，主观审美与文风不触发硬阻塞。
- [ ] AC8 发布详情可追溯品牌、渠道模板及素材版本；品牌升级后重试旧任务仍使用原版本，不重复交付成功渠道。
- [ ] AC9 旧任务在无新品牌版本字段的情况下仍可查看和按原行为重试。
- [ ] AC10 Notion 迁移可 dry-run、可重复执行、可核对数量；待核对草稿不自动成为有效品牌配置，来源资料保留。
- [ ] AC11 对比实施前后的代表性发布步骤，记录减少的重复录入与人工处理步骤。

## 范围外（首版不做）

- 多品牌、多租户、审批链、可视化模板编辑器、通用规则引擎、完整数字资产管理系统。
- AI 生图、自动封面生成、自动裁切、品牌效果分析。
- 通用任务/工作流系统。
